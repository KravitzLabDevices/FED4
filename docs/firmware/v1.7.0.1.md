### Group A — the terminal death (FSM stopped)

**1. Shorter measurement** — `TOUCH_MEASURE_CYCLES` 2000 → **200**

*Why.* IDF recommends sizing this so one measurement takes ~1 ms. At 2000 cycles Left measured **9.7 ms** (170,000 counts ÷ 17.5 MHz RTC_FAST) — a 10× overshoot. The raw value *is* the elapsed clock-cycle count, so a loaded pad scales it directly: the fatal poke read 2,343,997 counts, 13.8× baseline, which ran out of range and stopped the FSM.

*How it resolves it.* Left's baseline drops to ~17,000 counts, so the same 13.8× load reads ~241,000 — comfortably in range. Headroom goes from ~10× to ~130×. It also fixes a quieter problem: at a 22 ms scan cycle the 5 ms confirm window and 20 ms characterization interval were **re-reading the same hardware value**, which is why `StdL` was 37.5 on a 170,000 baseline (0.02 %) and the "3 agreeing samples" vote was vacuous.

**2. Measurement-timeout recovery** — `touch_pad_timeout_set` / `touch_pad_timeout_resume`

*Why.* v1.7.0 registered the ISR for `TOUCH_PAD_INTR_MASK_ACTIVE` only. `touch_sensor.h` warns that without `touch_pad_timeout_resume()`, *"the touch FSM will stop the measurement after timeout interrupt."* That is exactly what happened — all six registers froze together and stayed frozen 24 h.

*How it resolves it.* Threshold is `TOUCH_MEASURE_CYCLES × TOUCH_TIMEOUT_MULTIPLIER` = 200 × 700 = 140,000 counts (~8× the largest pad's nominal), expressed as a multiplier so it auto-scales if cycles are retuned. The ISR flags and counts the event; `fed4TouchServiceTimeout()` resumes from task context and prints `Touch: measurement timeout — FSM resumed`. An out-of-range reading costs one measurement instead of the device.

### Group B — wrong-pad identification

**3. ISR latches the status-mask edge, not scan position**

*Why.* v1.7.0 stored `touch_pad_get_current_meas_channel()` — whichever channel the FSM is scanning *now*, not the one that raised the interrupt. Against ms-scale measurements the ISR always lands on the **next** channel in scan order (Left=ch1 → Right=ch2 → Center=ch3), producing a deterministic one-channel rotation: touch Right → reports Center, touch Left → reports Right, touch Center → reports Left. The log's modal `LatchPad` matches all three predictions.

*How it resolves it.* `sTouchActiveMask |= (status & ~sTouchPrevStatus)` uses `touch_pad_get_status()`, the register that actually says which channel is active — the same source NG's `event->chan_id` derived from. Taking the **edge** rather than the level matters specifically here: after Left's benchmark stranded, Left sat permanently in `status`, and a level read would have credited Left on every wake forever. `TOUCH_PAD_INTR_MASK_INACTIVE` is handled too so `prevStatus` clears on release. `chan_id` is retained but logged as `IsrChan` — diagnostic only, never used for identification. `fed4TouchPadIndexFromLatchOnly()` returns a pad only when exactly one channel edged; zero edges returns 0 and falls through rather than guessing; multiple edges fall back to strongest `smooth − benchmark`, a physical measurement rather than a scan-position artifact.

**4. Confirm requires a real vote** — `ConfirmAgreed`

*Why.* `fed4TouchConfirmPadByAbsDelta()` returned its best single-sample candidate even with no agreeing run, and the arbiter gave confirm absolute priority. This is why the wrong-pad symptom appeared at ~30 h rather than at boot: the skew was at full strength from the first boot, but confirm (comparing `smooth − Idle`) was accurate while the sensor was healthy and overrode it. As the benchmark stranded and readings drifted from `Idle`, confirm abstained twice as often and the latch's deterministic error surfaced. In the log, `Pad == LatchPad` count *exactly equals* the confirm-abstention count in both eras (5/24 before, 15/34 after) — direct proof the latch only decided when confirm gave up.

*How it resolves it.* Confirm returns 0 unless it genuinely voted, so preferring it over a disagreeing latch is sound. This had to ship **with** change 3 — fixing the latch alone would have been worse, since more decisions fall through to it.

### Group C — permanent, unrecoverable states

**5. Characterization plausibility bounds + hardware gate** — `CalReject`

*Why.* This is what made the failure irreversible. With the FSM dead, `fed4TouchPadsReleased()` compared frozen `SmoothL` (2,343,997) against `IdleL` (170,729) → 1273 % rise → "stuck" → the 2 s rescue fired `fed4TouchCharacterizePads()`, which sampled a dead sensor 64 times (`Std = 0.0` on all three channels — a standard deviation of exactly zero across three independent channels is only possible if the hardware stopped) and wrote the garbage into `Idle`. `TOUCH_RISE_MIN` then **clamped Left's threshold upward**, inverting its own purpose: `rise = 800/2,343,997 = 0.000341` → clamped to 0.005 → `WakeAbsL = 11,719`, 14× the working value.

*How it resolves it.* Two independent guards, either sufficient:

- `fed4TouchAllPadsHwInactive()` gates the rescue on the **hardware** model (`smooth − bench < wakeAbs` on all three). With `SmoothL − BenchL = 2,179,318` vs `wakeAbs 853`, hardware says ACTIVE → rescue blocked. The old code trusted only the software model, which is the one that can be stuck.
- `TOUCH_CAL_MAX_IDLE_DEVIATION_FRAC` (0.10) rejects any per-pad `Idle` move beyond ±10 % of the first boot characterization; `TOUCH_CAL_MAX_RISE_MULT` (2.0) caps threshold growth.

This also closes the nastiest property of the old failure: writing `Idle = Smooth` made the rise fraction exactly 0, so "pads released" returned true and **the rescue never fired again**. The bad calibration silenced its own alarm — the sensor is validated against itself, so any frozen reading is by definition "released" once absorbed.

**6. Stale-benchmark watchdog** — `BenchReset (We may not need it implemented, only for troubleshooting)`

*Why.* A benchmark stranded *below* the true baseline latches its channel active, which is what freezes the benchmark — self-locking, no exit. v1.7.0 called `touch_pad_reset_benchmark()` nowhere, so no recovery path existed anywhere in the codebase. Note the irony of the 3.2.1 port: `fed4TouchApplyThresholds()` deliberately stopped restarting the FSM (*"would destroy drift tracking"*), which correctly fixed NG's bad-boot-seed problem — and in doing so deleted the only path that could ever reset a stranded benchmark. It traded *fails immediately, recoverable* for *survives a day, then fails permanently*.

*How it resolves it.* On `Heartbeat` rows only (never the poke path), if `smooth − bench >= wakeAbs` persists for `FED4_TOUCH_BENCH_STUCK_MS` (5 min), force a per-channel `touch_pad_reset_benchmark()`. The asymmetry makes this safe: stuck-**high** self-heals via the hardware IIR while the channel is inactive; stuck-**low** never does. 43 h of dead Left becomes 5 min.

**7. Bounded pre-sleep release wait** — `ReleaseWait` / `Stuck (We may not need it implemented, only for troubleshooting)`

*Why.* `while (!fed4TouchPadsReleased(...))` had no timeout and no break, and the rescue was one-shot per call. If pads never read released, `waitUntil()` never returns — device alive, logging nothing. This did not trigger in the field log, but it is a real trap and a hang teaches you nothing.

*How it resolves it.* `FED4_TOUCH_RELEASE_WAIT_MS` (5 s) forces a `break` and proceeds to sleep with the timer wake still armed, recording `ReleaseWaitMs`. A hang becomes a logged event.

### Group D — observability

**8. Touch diagnostic CSV** — appended **after** `WakeCount` so existing parsers and mixed-vintage `pd.concat` keep working:


| Columns                                        | Answers                                                                              |
| ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| `ScanPeriodUs`, `MeasUsL/C/R`                  | Did change 1 land? Is a pad creeping toward the timeout?                             |
| `TimeoutCount`                                 | Is change 2 firing, and when?                                                        |
