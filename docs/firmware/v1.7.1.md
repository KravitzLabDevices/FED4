## Pad ID (do not confuse these)

- **Software pad index** (`FedPad` / CSV `Pad` / `LatchPad` / `ConfirmPad`): Left=**1**, Center=**2**, Right=**3**.
- **Hardware touch channel** (`[FED4_Pins.h](../../src/FED4_Pins.h)`): Left=**1**, Right=**2**, Center=**3**.
- **Pad ID is Latch + Confirm.** `fed4TouchPadIndexFromLatchOnly()` uses the edge-accumulated `status_mask` (`touch_pad_get_status()`). Confirm is `fed4TouchConfirmPadByAbsDelta()` (`ConfirmAgreed`). Do **not** put `touch_pad_get_current_meas_channel()` back into the latch or the arbiter.
- `IsrChan` **is diagnostic only.** It is that current-scan-channel register at ISR entry — whichever channel the FSM happens to be scanning, not the channel that went active. Do not use it (or `PeakWinner = argmax(PeakL,C,R)`) as ground truth. Left idle can sit above a light Right poke (e.g. Left idle ~16880 beats a light Right poke ~16000).

## What this firmware keeps

Relative to un-instrumented 1.7.0 production touch. Sources: `[FED4_Touch.cpp](../../src/FED4_Touch.cpp)`, `[FED4_TouchHelpers.h](../../src/FED4_TouchHelpers.h)`, `[FED4_Sleep.cpp](../../src/FED4_Sleep.cpp)`.

Evidence is from the 74.7 h field log `FED4_0000_20260905_00_T.CSV` (4436 rows, 2026-09-05 12:21 → 09-08 14:57).


| #   | Change                         | Failure it fixes               |
| --- | ------------------------------ | ------------------------------ |
| 1   | Shorter measurement            | FSM stop (terminal)            |
| 2   | Measurement-timeout recovery   | FSM stop (terminal)            |
| 3   | ISR status-mask edge           | Wrong-pad identification       |
| 4   | Confirm vote                   | Wrong-pad identification       |
| 5   | Bounded pre-sleep release wait | Pre-sleep hang                 |
| 6   | Touch diagnostic CSV + version | Observability (off by default) |




### 1. Shorter measurement — `TOUCH_MEASURE_CYCLES` 2000 → **200**

*Issue.* IDF recommends sizing this so one measurement takes ~1 ms. At 2000 cycles Left measured **9.7 ms** — a 10× overshoot. The raw value *is* the elapsed clock-cycle count, so a loaded pad scales it directly: the fatal poke read 2,343,997 counts, 13.8× baseline, which ran out of range and stopped the FSM. At a 22 ms scan cycle the 5 ms confirm window was also re-reading the same hardware value, so the "3 agreeing samples" vote was vacuous.

*How it addresses it.* Left's baseline drops to ~17,000 counts, so the same 13.8× load reads ~241,000 — comfortably in range. Headroom goes from ~10× to ~130×. Confirm and characterization samples become independent.

### 2. Measurement-timeout recovery — `touch_pad_timeout_set` / `touch_pad_timeout_resume`

*Issue.* v1.7.0 registered the ISR for `TOUCH_PAD_INTR_MASK_ACTIVE` only. `touch_sensor.h` warns that without `touch_pad_timeout_resume()`, the touch FSM stops after a timeout interrupt. That is exactly what happened — all six registers froze together and stayed frozen 24 h.

*How it addresses it.* Threshold is `TOUCH_MEASURE_CYCLES × TOUCH_TIMEOUT_MULTIPLIER` = 200 × 700 = 140,000 counts (~8× the largest pad's nominal). The ISR flags and counts the event; `fed4TouchServiceTimeout()` resumes from task context. An out-of-range reading costs one measurement instead of the device.

### 3. ISR latches the status-mask edge, not scan position

*Issue.* v1.7.0 stored `touch_pad_get_current_meas_channel()` — whichever channel the FSM is scanning *now*, not the one that raised the interrupt. Against ms-scale measurements the ISR always lands on the **next** channel in scan order (Left=ch1 → Right=ch2 → Center=ch3), producing a deterministic one-channel rotation.

*How it addresses it.* `sTouchActiveMask |= (status & ~sTouchPrevStatus)` uses `touch_pad_get_status()`, the register that actually says which channel is active. Taking the **edge** rather than the level matters after a pad strands: a level read would credit that pad on every wake forever. `chan_id` is retained as `IsrChan` — diagnostic only, never used for identification.

### 4. Confirm requires a real vote — `ConfirmAgreed`

*Issue.* `fed4TouchConfirmPadByAbsDelta()` returned its best single-sample candidate even with no agreeing run, and the arbiter gave confirm absolute priority. While the sensor was healthy, confirm overrode the skewed latch; as readings drifted from Idle, confirm abstained and the latch's deterministic error surfaced.

*How it addresses it.* Confirm returns 0 unless it genuinely voted (`TOUCH_ID_CONFIRM_AGREE` agreeing samples), so preferring it over a disagreeing latch is sound. This had to ship **with** change 3.

### 5. Bounded pre-sleep release wait — `ReleaseWait` / `Stuck`

*Issue.* `while (!fed4TouchPadsReleased(...))` had no timeout. If pads never read released, `waitUntil()` never returns — device alive, logging nothing.

*How it addresses it.* `FED4_TOUCH_RELEASE_WAIT_MS` (5 s) forces a break and proceeds to sleep with the timer wake still armed, recording `ReleaseWaitMs`. A hang becomes a logged event (`Stuck` if the hard cap, `ReleaseWait` if slow but released).

### 6. Touch diagnostic CSV + version trackability

`_T.CSV` schema and `logTouch()` stay in the library, compiled out when `FED4_ENABLE_TOUCH_LOG` is 0. When enabled: BootChar / Heartbeat / Poke / TouchMiss / Rechar / Stuck / ReleaseWait. Columns after `WakeCount`: `ScanPeriodUs`, `MeasUs{L,C,R}`, `TimeoutCount`, `StatusMask`, `IsrChan`, `IsrMask`, `IsrCount`, `Peak{L,C,R}`, `ConfirmAgreed`, `ReleaseWaitMs`.

Firmware identity `v1.7.1` is on the display footer, in the Serial boot line, and in CSV `LibraryVer`. Drift sketches report `AwakeDrift` / `SleepDrift`.

| `smh_lvl = TOUCH_PAD_SMOOTH_OFF`                             | Smooth *is* raw                                                         | Zero rejection of a single bad sample. 22 % of pokes in the field log contaminated another pad's reading. |
